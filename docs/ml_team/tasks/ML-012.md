# ML-012. Сделать понятную управляющему выдачу и журнал правок

**Приоритет:** P1 · **Роль:** ML Engineer + аналитик · **Поставка:** R3

**Оценка:** 2 человеко-дн. активной работы. Ожидание данных и наблюдение считаются отдельно.

**Статус:** proposed — постановка подготовлена; исполнитель и календарная дата ещё не назначены.

**Зависимости:** ML-001, ML-011.

## Цель

Дать управляющему проверяемую рекомендацию и собрать причины несогласия.

## Входы

Общая постановка: `docs/ml_team/brief.md`; результаты прототипа: `reports/results.md` и `reports/research/results.md`. Артефакты зависимых задач должны быть приняты до начала работ. Для задач внедрения нужны данные пилотной пекарни; открытый исторический набор их не заменяет.

## Работы

1. Подготовить CSV или простую таблицу: дата, SKU, прогноз, диапазон, рекомендация, текущий план, статус данных.
2. Добавить дату отсечения, версию модели и краткие понятные причины изменения прогноза.
3. Записывать исходную рекомендацию, окончательный план, автора, время и причину override.

## Результат поставки

- `ui_or_export/`
- `override_log.schema.json`
- `manager_feedback.md`

## Критерии приёмки

- [ ] Управляющий выполнил 3 сценария: обычный день, акция, неполные данные.
- [ ] Исходный прогноз не перезаписывается ручным решением.
- [ ] Низкая уверенность и fallback видны; рекомендация не отправляется в производство автоматически.

## Порядок сдачи

PR с артефактами и свидетельствами проверок; ревью владельца роли по плану поставки. Имена файлов выше — ожидаемые будущие результаты задачи, а не утверждение об их наличии. При отсутствии входов указать блокер и владельца; не заменять фактические данные вымышленными.
