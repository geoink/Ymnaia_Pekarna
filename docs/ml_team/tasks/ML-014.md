# ML-014. Добавить мониторинг и резервный режим

**Приоритет:** P0 · **Роль:** ML Engineer + Data Engineer · **Поставка:** R3

**Оценка:** 3 человеко-дн. активной работы. Ожидание данных и наблюдение считаются отдельно.

**Статус:** proposed — постановка подготовлена; исполнитель и календарная дата ещё не назначены.

**Зависимости:** ML-003, ML-012, ML-013.

## Цель

Обнаруживать пропуски и ухудшения до использования некорректного плана.

## Входы

Общая постановка: `docs/ml_team/brief.md`; результаты прототипа: `reports/results.md` и `reports/research/results.md`. Артефакты зависимых задач должны быть приняты до начала работ. Для задач внедрения нужны данные пилотной пекарни; открытый исторический набор их не заменяет.

## Работы

1. Контролировать свежесть/полноту, новые SKU, ошибки исполнения, bias и качество по товарам после появления факта.
2. Настроить пороги на исторических данных и согласовать получателя уведомлений.
3. Реализовать переход на одобренный baseline при достаточной истории, иначе на ручное решение.

## Результат поставки

- `monitoring_spec.md`
- `alerts/`
- `fallback_policy.md`

## Критерии приёмки

- [ ] Пройдены сценарии: недоставленная выгрузка, новый SKU, повреждённый артефакт и резкий сдвиг продаж.
- [ ] Каждый сценарий даёт правильный статус и понятную инструкцию управляющему.
- [ ] Запоздалый факт не используется для скрытого исправления ранее выданного прогноза.
- [ ] Пороги и ответственность утверждены до shadow-режима.

## Порядок сдачи

PR с артефактами и свидетельствами проверок; ревью владельца роли по плану поставки. Имена файлов выше — ожидаемые будущие результаты задачи, а не утверждение об их наличии. При отсутствии входов указать блокер и владельца; не заменять фактические данные вымышленными.
