# ML-006. Зафиксировать доступность признаков в момент прогноза

**Приоритет:** P0 · **Роль:** Data Scientist + Data Engineer · **Поставка:** R2

**Оценка:** 2 человеко-дн. активной работы. Ожидание данных и наблюдение считаются отдельно.

**Статус:** proposed — постановка подготовлена; исполнитель и календарная дата ещё не назначены.

**Зависимости:** ML-003, ML-004.

## Цель

Исключить использование фактов, которые ещё не были известны при составлении плана.

## Входы

Общая постановка: `docs/ml_team/brief.md`; результаты прототипа: `reports/results.md` и `reports/research/results.md`. Артефакты зависимых задач должны быть приняты до начала работ. Для задач внедрения нужны данные пилотной пекарни; открытый исторический набор их не заменяет.

## Работы

1. Для каждого признака описать event_time, available_at, сдвиг, источник и обработку пропусков.
2. Переиспользовать один код признаков в backtest и вечернем расчёте.
3. Проверить календарь, лаги, цены и будущие акции; погоду добавлять только из исторически доступного прогноза.

## Результат поставки

- `feature_contract.md`
- `src/features/`
- `tests/test_point_in_time.py`

## Критерии приёмки

- [ ] Изменение текущих и будущих продаж не меняет признаки текущей даты.
- [ ] Поздно пришедший факт не попадает в исторический прогноз раньше available_at.
- [ ] Для заданной даты признаки batch-расчёта совпадают с исторической симуляцией.

## Порядок сдачи

PR с артефактами и свидетельствами проверок; ревью владельца роли по плану поставки. Имена файлов выше — ожидаемые будущие результаты задачи, а не утверждение об их наличии. При отсутствии входов указать блокер и владельца; не заменять фактические данные вымышленными.
