# ML-003. Построить загрузку кассовых данных с контролем полноты

**Приоритет:** P0 · **Роль:** Data Engineer · **Поставка:** R1

**Оценка:** 4 человеко-дн. активной работы. Ожидание данных и наблюдение считаются отдельно.

**Статус:** proposed — постановка подготовлена; исполнитель и календарная дата ещё не назначены.

**Зависимости:** ML-001, ML-002.

## Цель

Получать одинаковую историю продаж при повторной загрузке и исправлении чеков.

## Входы

Общая постановка: `docs/ml_team/brief.md`; результаты прототипа: `reports/results.md` и `reports/research/results.md`. Артефакты зависимых задач должны быть приняты до начала работ. Для задач внедрения нужны данные пилотной пекарни; открытый исторический набор их не заменяет.

## Работы

1. Реализовать контракт из brief.md: store_id, sku_id, line_id, business_date, event_time, available_at, quantity, price, operation.
2. Сохранять версию выгрузки и время доступности; отделить событие продажи от поздней корректировки.
3. Добавить проверки схемы, уникальности line_id+version, полноты дат и уведомление при недоставке.

## Результат поставки

- `src/ingestion/`
- `schemas/pos.schema.json`
- `reports/data_quality.md`

## Критерии приёмки

- [ ] Повторная загрузка одного файла не удваивает продажи.
- [ ] Синтетические случаи дубля ID, возврата и поздней корректировки дают ожидаемый результат.
- [ ] Контрольные суммы итогов за выбранные дни сверены с кассой; расхождения объяснены.
- [ ] При недоставке данных прогноз помечается как недоступный, а не как нулевые продажи.

## Порядок сдачи

PR с артефактами и свидетельствами проверок; ревью владельца роли по плану поставки. Имена файлов выше — ожидаемые будущие результаты задачи, а не утверждение об их наличии. При отсутствии входов указать блокер и владельца; не заменять фактические данные вымышленными.
