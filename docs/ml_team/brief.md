# Постановка проекта для ML-команды

## Заказчик и решение

Заказчик — владелец небольшой пекарни. Каждый вечер после закрытия управляющий составляет план выпечки на следующий рабочий день по восьми пилотным SKU. Система должна вовремя выдать прогноз продаж, диапазон неопределённости и рекомендацию по выпуску с объяснением статуса данных. Окончательное решение принимает управляющий; его правки сохраняются.

Название проекта: **«Прогнозирование продаж и поддержка планирования выпечки для небольшой пекарни»**. Использование ML в пекарнях уже описано в исследованиях; новизна этой работы — проверка доступного воспроизводимого решения и его пригодности в конкретном процессе, а не заявление о первом применении ML. См. [обзор исследований](../research_review.md).

## Исходное состояние и целевой результат

**Уже сделано в R0:** воспроизводимый учебный эксперимент на открытых данных одной французской пекарни; восемь товаров; однодневный прогноз; сравнение пяти методов, дополнительная проверка девяти вариантов на 11 окнах; ноутбук, отчёты, презентация и тесты.

**Нужно сделать в R1–R4:** подключить данные конкретной пекарни, проверить модель на новом периоде, учесть доступность товара и стоимость выпуска, проверить ежедневную работу, провести контролируемый пилот. Все 18 задач в [бэклоге](backlog.md) — будущие работы, не уже выполненное внедрение.

В первом внедрении не требуются нейросети, мобильное приложение и онлайн-API. Достаточны ежедневный пакетный расчёт и понятная таблица. Автоматический заказ сырья и автоматическая отправка задания в производство не входят в первую поставку.

## Гипотезы и критерии решения

| Гипотеза | Проверка | Критерий до запуска |
|---|---|---|
| История продаж и календарь дают преимущество перед простыми правилами | Временные окна и новый закрытый тест | Предлагаемый ориентир: относительное снижение WAPE ≥5% против лучшего baseline, выбранного на валидации; проверить MAE, macro MASE7/RMSSE7 и bias по SKU. Утвердить пороги в ML-007 до теста |
| Учёт стоимости и ограничений улучшает план | Сценарии на реальных затратах; ограничения партий/печи | Все планы выполнимы; сценарные выводы явно отделены от фактических |
| Использование рекомендаций улучшает финансовый результат | Контролируемый пилот | Положительный эффект на основную денежную метрику с заранее выбранным уровнем неопределённости и без нарушения guardrails. MDE, пороги и мощность задаются в ML-016 |

Если ML не проходит сравнение, допускается поставка простого метода. Успех проекта определяется полезностью решения, а не сложностью модели. Новую модель не выбирают по августу–сентябрю 2022: этот период уже изучен.

## Метрики

- **Прогноз:** WAPE по всему ассортименту, MAE в штуках, macro MASE7/RMSSE7, bias по SKU и по времени, худший месяц. Нулевой знаменатель метрики отмечается как неопределённый. Масштабы MASE/RMSSE берутся только из обучения.
- **Неопределённость:** pinball loss для каждой квантили, фактическое покрытие и ширина интервалов; отдельно для известных периодов отсутствия товара.
- **Основная бизнес-метрика пилота, предлагаемая к согласованию:** вклад в прибыль на открытый магазин-день: выручка за вычетом переменных затрат на весь выпуск, затрат на утилизацию и распределённых затрат системы. Точная бухгалтерская формула и сопоставимость цен утверждаются с заказчиком.
- **Сопутствующие:** стоимость списаний на магазин-день, доля списаний от выпуска, доля подтверждённого времени отсутствия товара. Неизвестное наличие не считается доступностью.
- **Guardrails:** доступность ключевых SKU, нагрузка персонала, число невыполнимых рекомендаций и опоздавших расчётов. Порог допустимого ухудшения задаётся до пилота.

Снижение прогнозируемой вероятности или числа продаж само по себе не является улучшением бизнеса. Действие — изменение плана выпуска; эффект этого действия проверяется отдельно.

## Контракт данных для пилота

| Поток | Минимальные поля | Зачем |
|---|---|---|
| Касса | store_id, sku_id, line_id, version, business_date, event_time, available_at, quantity, unit_price, operation | История продаж, возвраты, повторная загрузка, доступность факта в прошлом |
| Работа магазина | store_id, date, open_status, open_at, close_at, source | Отличать закрытие от пропуска выгрузки |
| Ассортимент | store_id, sku_id, active_from, active_to, unit, batch_size | Не превращать неактивный SKU в нулевой спрос |
| Наличие и выпуск | store_id, sku_id, timestamp, opening_stock, production, receipts, sales, waste, transfers, closing_stock | Баланс товара и фактические списания |
| Исчерпание товара | store_id, sku_id, start_at, end_at, observation_status, source | Цензурирование продаж наличием |
| Экономика | sku_id, valid_from, price, variable_cost, salvage_value, disposal_cost | Цена ошибки и сценарии выпуска |
| План и правки | date, sku_id, forecast, model_version, cutoff, recommended_qty, final_qty, override_reason, decided_at | Сравнение рекомендаций с реальными действиями |

Формат первой интеграции — CSV UTF-8 или Parquet с описанной схемой. Временная зона задаётся для магазина; UTC-время события хранится отдельно от business_date. Неизвестные значения — null, не 0. Дедлайн появления данных определяется в ML-001; просрочка видна в выдаче. Фамилии покупателей, номера карт и клиентские контакты для задачи не нужны.

## Схема ежедневной работы

```mermaid
flowchart LR
    A[Касса, выпуск, остатки] --> B[Проверка схемы и полноты]
    B --> C[Признаки на дату отсечения]
    C --> D[Прогноз и диапазон]
    D --> E[План с ограничениями]
    E --> F[Проверка управляющего]
    F --> G[Итоговый план и журнал правок]
    G --> H[Фактические продажи, остатки, списания]
    H --> I[Мониторинг и оценка]
    B --> J[Резервный метод или ручной план]
    J --> F
```

## Ответственность

| Роль | Решения и приёмка |
|---|---|
| Product Owner / владелец пекарни | Экономика, рабочий процесс, ассортимент, пилот и решение о внедрении |
| ML Lead | Протокол оценки, выбор версии, переход между этапами, техническое ревью |
| Data Scientist | Признаки, backtest, baselines, квантили, модель спроса и планирование |
| Data Engineer | Договорённости по источникам, загрузка, календарь, качество и версии данных |
| ML Engineer | Ежедневный запуск, артефакты, выдача, мониторинг и восстановление |
| Аналитик | Метрики, мощность эксперимента, анализ пилота, коммуникация с управляющим |
| Управляющий | Учёт фактов, проверка плана, причины ручных правок |

Это роли, а не назначенные сотрудники. Один человек может совмещать роли; независимое ревью протокола и результатов желательно сохранить. Рабочие инструменты: GitHub Issues для задач, PR для поставок, версия данных и конфигурация эксперимента для каждого отчёта.
